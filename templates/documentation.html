1. Project Overview

The Student Academic Progression and Portfolio Management System is a full-stack DBMS application engineered to address the critical challenges of monitoring student academic trajectories, prior qualifying records, multi-semester SGPA/CGPA trends, theory versus laboratory performance, portfolio achievements, and formal academic leave/gap intervals.

Unlike conventional student databases that flatten records into single monolithic spreadsheets with rampant redundancy, this system implements a rigorous relational schema normalized to Third Normal Form (3NF), powered by MySQL 8.0, Flask, Chart.js, and Google Sheets API integration.

2. Technology Stack

Frontend Tier
  • HTML5 & CSS3: Semantic markup, custom white & dark blue design tokens.

  • Chart.js: Dynamic SGPA/CGPA progression curves with gap point annotations and distribution charts.
  • Bootstrap Icons: Modern UI glyphs and iconography.

3. Database Design & 3NF Normalization Analysis

A relational database is in Third Normal Form (3NF) if and only if it is in 2NF and every non-prime attribute is non-transitively dependent on every candidate key. The system enforces 3NF across 8 distinct entities:

Entity Table Candidate / Primary Key 1NF (Atomicity) 2NF (No Partial Dependency) 3NF (No Transitive Dependency)
students student_id, roll_no Every column holds atomic values. No multivalued phone or mark lists. Single-column primary key; partial dependency cannot exist. All attributes (name, email, status) depend directly on the student key.
academic_history history_id Atomic qualification entries (Secondary, Higher Secondary, Diploma). Separated from students to eliminate repeating columns. Marks and percentages relate solely to the specific prior degree record.
semesters semester_id (Alt: student_id, semester_no) Atomic semester numbers, SGPA, CGPA, gap indicators. All grade points depend fully on (student_id, semester_no). Eliminates transitive semester attributes from the parent student entity.
subjects subject_id, subject_code Course code, course name, type (Theory/Lab), credits. Subject definition is independent of any specific student enrollment. Credits and course types depend solely on the subject candidate key.
semester_subject_marks mark_id (Alt: semester_id, subject_id) Internal, external, practical, total, and letter grade. Junction table resolving the Many-to-Many relationship between semesters and subjects. Marks are dependent entirely on the junction pair (semester_id, subject_id).
seminars seminar_id Title, seminar_type (Internal/External), date, organizer, certificate. Prevents multi-valued presentation arrays inside student rows. Presentation details depend strictly on the seminar primary key.
activities activity_id Title, activity_type, role, date, organizer. Separates portfolio events into discrete normalized records. Attributes describe the activity event, eliminating transitive redundancy.
drop_years drop_id Start year, end year, official justification. Independent interval entity for tracking academic hiatuses. Dates and justification depend only on the drop interval key.

4. Relational Constraints & Integrity Enforcement

  • Primary Keys & Auto-Increment: Surrogate integer primary keys ensure fast indexing and immutable join identities.
  • Unique Keys: students.roll_no (unique roll number), students.email, subjects.subject_code, UNIQUE(student_id, semester_no) (prevents duplicate semester entries), UNIQUE(semester_id, subject_id) (prevents duplicate marks entries for the same course in a semester).
  • Foreign Key Cascades: Dependent tables utilize ON DELETE CASCADE referencing parent keys. Deleting a student safely cascades to remove related academic records without leaving orphaned rows.
  • MySQL 8 CHECK Constraints: chk_sgpa CHECK (sgpa BETWEEN 0 AND 10), chk_cgpa CHECK (cgpa BETWEEN 0 AND 10), chk_semester_no CHECK (semester_no BETWEEN 1 AND 12), chk_history_percentage CHECK (percentage BETWEEN 0 AND 100), chk_drop_years CHECK (year_end >= year_start), chk_max_marks CHECK (max_marks > 0).

5. Complete Working CRUD Operations

All eight entities support full Create, Read, Update, and Delete operations using parameterized SQL statements (e.g. %s placeholders in MySQL Connector) to neutralize SQL Injection vulnerabilities:

1. Students: /students, /students/add, /students/edit/<id>, /students/delete/<id>
2. Academic History: /academic-history, /academic-history/add, /academic-history/edit/<id>, /academic-history/delete/<id>
3. Semesters: /semesters, /semesters/add/<id>, /semesters/edit/<id>, /semesters/delete/<id>

6. Google Sheets One-Way Synchronization Protocol

The Google Sheets synchronization engine executes a snapshot push using gspread and google-auth:

  1. The application queries relational snapshots from MySQL for all 8 entities.
  2. It authenticates via Google Cloud Service Account credentials (GOOGLE_CREDENTIALS).
  3. It connects to the Google Spreadsheet specified by GOOGLE_SHEET_ID.
  4. For each entity table, it verifies or automatically generates the target worksheet tab (Students, Academic_History, Semesters, Subjects, Semester_Marks, Seminars, Activities, Drop_Years).
  5. It clears the worksheet contents and bulk updates the header and row values with value_input_option='USER_ENTERED'.

Answer: An unnormalized design would store student details, qualifying marks, multi-semester grades, and seminar arrays in a single table, causing update, deletion, and insertion anomalies. In our schema:
1. 1NF: All attribute values are atomic (no repeating groups or comma-separated lists).
2. 2NF: Every table has single-column keys or composite keys where all non-key attributes depend on the entire primary key.
3. 3NF: There are no transitive dependencies (e.g. subject credits depend on subject_id, not student_id; gap records depend on drop_id). Thus, every non-prime attribute depends only on the primary key, directly and non-transitively.

Answer: A Many-to-Many relationship exists between semesters and subjects: a semester has multiple subjects, and the same subject code is enrolled across multiple students' semesters. We resolve this using the junction table semester_subject_marks, which carries foreign keys to both parent tables and enforces a composite UNIQUE KEY (semester_id, subject_id) to prevent duplicate grade entries for the same course in any given semester.

Answer: ON DELETE CASCADE guarantees referential integrity at the database engine level. If a student is removed from students, MySQL InnoDB automatically removes all their dependent academic history, semester scores, marks, seminars, and activity records. This prevents orphaned records from cluttering the database and ensures consistency even if a delete command is issued directly in SQL Workbench.

Answer: The system enforces a defense-in-depth architecture:
1. Frontend / HTML5: required, min, max, step, type="email" for immediate user feedback.
2. Backend / Python: Range checks, null conversions, try-catch error trapping with informative flash messages.
3. Database / MySQL 8: Declarative CHECK constraints (e.g. sgpa BETWEEN 0 AND 10, year_end >= year_start) and UNIQUE constraints that reject illegal data even under concurrent or manual execution.

Answer: In enterprise and institutional DBMS architectures, the relational database must maintain the authoritative Single Source of Truth (SSOT). Allowing unvalidated two-way edits from arbitrary spreadsheet cells back into MySQL would bypass relational constraints, type checks, and referential integrity. Therefore, one-way synchronization publishes snapshot reports safely to stakeholders while retaining MySQL as the authoritative transaction ledger.
